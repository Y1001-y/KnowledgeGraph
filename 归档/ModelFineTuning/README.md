## 一、当时的方法

### 1.1 目标

从 BOSS 直聘的岗位描述（JD）里抽出技能，作为「江苏互联网 AI 岗位市场技能需求统计」的
数据基础。当时的判断是：需要模型读懂 JD 的语义，规则做不干净，所以要微调一个专用模型。

```
输入: 岗位名称 + 职位类别 + JD 前 1200 字符
输出: 该岗位要求的技术技能列表（顿号分隔，如 Java、MySQL、Redis）
```

### 1.2 技术栈

| 项 | 选择 |
|---|---|
| 训练框架 | Unsloth + TRL `SFTTrainer` |
| 微调方式 | QLoRA（4bit 底座 + LoRA adapter） |
| 底座 | `unsloth/Qwen3-8B-unsloth-bnb-4bit`（预量化，约 7GB） |
| 环境 | WSL2 Ubuntu + RTX 5070 Ti Laptop 11.94GB（sm_120，需 torch 2.11+cu128） |
| 数据格式 | Alpaca 格式 SFT jsonl |

### 1.3 数据流水线

```
Origin data/*.csv（BOSS 直聘 20874 行 × 125 列）
  └─ Scripts/prepare_dataset.py
       ├─ 全量转 Excel
       ├─ 按 JD 正文（去空白）去重，杜绝训练/测试泄漏
       ├─ 正则词典抽技能（209 条规范名，覆盖编程语言 / 前端 / 后端框架 /
       │   数据库 / 大数据 / AI / 运维 / 测试 / 嵌入式）
       ├─ 剔除无技能命中的岗位
       ├─ 前 n 行 → 测试集，其余 → 训练集
       ├─ 技能统计（含重复 / 去重岗位 双口径）
       └─ 生成 SFT jsonl
```

最终规模：**训练 8982 条 / 测试 498 条，覆盖 208 种技能**。

去重岗位口径下的技能频次（20073 个岗位）：Python 22.96%、Java 18.83%、C++ 15.43%、
MySQL 14.05%、C语言 7.81%、Spring 7.44%、大模型/LLM 7.40%、C# 7.36%。

### 1.4 训练配置

| 参数 | 值 |
|---|---|
| LoRA r / alpha | 16 / 32 |
| target_modules | q, k, v, o, gate, up, down（7 个线性层全挂） |
| max_seq_length | 1024 |
| batch / 梯度累积 | 1 / 8 |
| learning_rate / scheduler | 2e-4 / cosine |
| epochs | 1 |
| 显存优化 | 4bit + adamw_8bit + `use_gradient_checkpointing="unsloth"` |
| 可训练参数 | 43.6M / 8.23B（0.53%） |
| 训练技巧 | chat template 关闭思考模式；`train_on_responses_only` 只对回复段算 loss |

OOM 时的降级顺序：先降 `max_seq_length` 到 512，再减 `gradient_accumulation_steps`。

### 1.5 两版实验

| 版本 | 标签口径 | 规模 | 结果 | 结论 |
|---|---|---|---|---|
| v1 | 词典抽取 **∪** 平台 `showSkills` 标签 | 14218 条，1776 步，2h01m | train_loss 0.7619，mean_token_accuracy 84.2%，Micro-P 0.28 | 平台标签含「工作简单」「可带手机」等非技能噪声，标签被污染，模型表现为「多答」；格式学会了，标签质量是瓶颈 |
| v2 | 纯词典抽取 | 9518 条 | 预测与标答同口径，预期 Micro-F1 明显高于 v1 的 0.369 | 口径统一后指标可读，但见下节 |

### 1.6 踩过的坑（细节见 `../../FineTuning/Docs/训练记录.md`）

1. `HF_HUB_OFFLINE=1` 但模型不在缓存 → `LocalEntryNotFoundError`
2. hf-mirror + Xet 报 401（`hf_xet` 走独立存储后端，镜像站不代理）→ `HF_HUB_DISABLE_XET=1`
3. Unsloth 的参数名是 `model_name` 而非 `model_name_or_path`，写错会被 `**kwargs` 吞掉且静默回落到默认模型
4. TRL 新版改名：`max_seq_length`→`max_length`、`tokenizer`→`processing_class`、`warmup_ratio`→`warmup_steps`
5. Qwen3 思考模式吞掉输出额度，只吐 `<think>` 片段 → `enable_thinking=False`
6. 欠训练阶段复读（`C++、C++、C++…`）→ `repetition_penalty=1.15`，根本解决靠训练步数

## 二、停止的技术原因

五条技术原因，第一条是结构性的——它决定这条路线能达到的上界，后四条是工程可行性约束。
三条路线的横向对比见 [`../README.md`](../README.md) 第一节。

### 2.1 监督信号与任务同源，输出上界被标答锁死（结构性原因）

设标注函数 `f` = `prepare_dataset.py` 的 209 条正则词典，训练得到 `g ≈ f`。
`f` 只做字面匹配、不含语义信息，因此 `g` 的信息上界等于 `f` 的信息上界。机理上表现为三点：

| 机理 | 表现 |
|---|---|
| 输出空间受限 | 标答取值域就是词典的规范名集合，模型不会输出集合外的技能；未登录词在训练集中**无正样本、无对应梯度** |
| 信息增益为零 | `g(JD) ≈ f(JD)`，而 `f` 只需几十行正则即可执行。用 8B 逼近一个脚本，不引入新信息 |
| 学习目标偏移 | 模型实际拟合的是「JD → 复现词典输出」，而不是「JD → 技能集合」的语义关系。换个评估口径立刻暴露：v1 的 Micro-P 0.28 就是标签口径与新口径错位的直接结果 |

关键矛盾在于：模型唯一有存在价值的地方是词典覆盖不到的长尾（新技能、隐含表达、软技能），
而**长尾恰好没有标注**——标注函数标不出来的东西，也就没有监督信号。
打破这个闭包只有两条路：引入人工金标准，或引入词典之外的信息源。

- 人工标注 14 万条 JD → 成本远高于直接调用云端大模型做首轮抽取
- 引入更强模型产出标答再蒸馏 → 这正是当前路线三的第一步（先有干净标答，再谈微调）

### 2.2 12GB 单卡下，训练与推理吞吐不满足数据规模

| 环节 | 实测 / 估算 | 约束 |
|---|---|---|
| 训练 1 epoch（8982 条） | 2h01m，1776 步 | `8B + 1024 长度` 已吃满 11.94GB，`batch_size` 只能为 1，无并行余量，只能靠梯度累积 |
| 本地推理 14 万条 | 数天（单卡串行） | 显存占满后无法多实例并发，吞吐被硬件线性锁死 |
| 云端同模型 14 万条 | 3 并发 18h / 5 并发 10h，约 ¥30 | 无显存约束，并发可调 |

本地部署的唯一优势是数据不出本机，但招聘 JD 属公开招聘信息，不存在出域合规问题。

### 2.3 迭代周期的量级差异

抽取的边界规则（「自动驾驶」算不算技能、「车辆/行人」是不是被操作对象、
「标注准确率」是不是考核指标而非技能）只能靠反复试错逼近。两条路线的单轮成本：

| | 路线二（微调） | 路线三（prompt） |
|---|---|---|
| 改一处边界 | 改标签口径 → 重跑 `prepare_dataset` → 重训 2h → 重新评估 | 改一句 prompt → 数十秒出新结果 |
| 一轮验证 | 半天 | 几分钟 |
| 回滚 | 依赖 checkpoint | 文本回退 |

单轮差 100 倍，意味着微调路线**无法支撑"改一条规则看一眼结果"的工作方式**，
而这类任务恰好只能这样磨。

### 2.4 任务错配：抽取需要语义先验，二分类不需要 8B 容量

原设计是「云端抽取 + 本地微调模型分类」，拆开看是两个性质不同的子问题：

| 子任务 | 输入 → 输出 | 所需能力 | 合适载体 |
|---|---|---|---|
| 抽取 | JD 全文 → 技能集合（开放集） | 语义理解、边界判断、先验知识 | 8B 级生成式模型（云端） |
| 硬/软二分类 | 岗位名 + 技能词 + 所在句 → 2 类 | 句内特征分类，闭集 | 100M 级编码器（本地） |

二分类的输入信息量极小、标签空间只有 2 维，`chinese-roberta-wwm-ext`（102M）足够，
且比 8B 快约两个数量级、可 CPU 推理、可解释。用 8B 做二分类是容量浪费，
同时把「生成式随机性」引入了一个要求确定性的环节——这会破坏频次统计的可比性。

结论：微调这件事本身没有被否定，是**训错了对象**——该训的是分类器（小模型），不是抽取器（大模型）。

### 2.5 抽取噪声的收敛点在数据后处理，不在模型精度

即使抽取质量再高，`自动驾驶`（领域名）、`标注准确率`（考核指标）、`五险一金`（福利）
这类词仍会进入结果。指望 prompt 达到 100% 精确不现实；工业做法是抽完过一道黑名单：

- 可审计：每条被过滤的词都能追到规则
- 可增量：发现一个新误抽就加一行，不需要重训
- 可写进论文：属正当的「数据后处理」环节

这条认识把「模型必须很准」的压力转移到可控的规则层，同时让"用更大模型/更多训练换精度"
的边际收益进一步下降。

## 三、路线调整结论

```
路线二（停用）                    路线三（当前）
─────────────────────────────   ─────────────────────────────
本地 Qwen3-8B + QLoRA 微调       云端 Qwen3-8B（硅基流动免费 / 百炼 ¥0.5 每百万）
  ↓ 训练 2h                        ↓ prompt 迭代，分钟级
本地模型推理 14 万条（数天）       云端并发 3–5，18h 内跑完，约 ¥30
  ↓                               ↓
8B 做二分类                       chinese-roberta 做二分类（100M，快 100 倍）
  ↓                               ↓
统计                             统计 + 后处理黑名单过滤
```

判定依据是三条约束的交集（完整推导见 [`../README.md`](../README.md) 第二节）：

| 约束 | 内容 | 排除了什么 |
|---|---|---|
| 信息源 | 抽取要覆盖开放集、要能区分对象词/领域词/指标词 → 需要词典之外的新信息 | 路线一（无新信息）、路线二（上界 = 词典） |
| 一致性 | 频次统计要求同一技能永远同一类，跨批次可比 | 把二分类交给生成式模型的任何方案 |
| 成本 | 14 万条 × 多轮边界迭代，单轮要便宜且快 | 本地单卡推理（天级/轮）、为调边界重训（2h/轮） |

一句话：**把「读懂文本」交给生成式模型（信息来自预训练语料），把「保持口径」交给
确定性代码（可靠性来自没有随机性），把可训练的部分压缩到真正需要模型的二分类上。**

模型和训练脚本已删，但这条路线里可复用的资产都留在了 `FineTuning/`：

| 保留物 | 为什么还留着 |
|---|---|
| `Datasets/Processed/`（训练集 8982 + 测试集 498 + 技能统计） | 数据本身和模型无关。测试集可作为后续分类器的评估集；技能统计是历史基线，可和新结果对比 |

| `infer_csv.py` | 读 CSV → 批量推理 → 写回结果的骨架，换个后端就是云端抽取脚本 |
| `Datasets/Samples/jd-sample-10.txt`（**已迁出**） | 10 条固定样本，保证每轮迭代在同一批数据上对比。现位于 `../../Cleaning/eval/jd-sample-10.txt`，在清洗管线里作 dev / test 评估集 |
| `Docs/训练记录.md` | 6 条踩坑，其中 Qwen3 思考模式、TRL 参数改名对云端调用同样适用 |
| `Outputs/prompt/20261102/001.txt`（**已迁出**） | 内容是 **v2 prompt 对 10 条样本的抽取结果快照**（不是 prompt 历史）。现位于 `../../Cleaning/eval/results/20261102-run1.jsonl`，作为精度基线 |

已删除：LoRA adapter ×3、optimizer 状态 ×2、tokenizer、trainer_state（454M）、
Unsloth 编译缓存（2.6M）、4 个训练/评估脚本、评估与预测产物（89K）。
`FineTuning/` 从 541M 降到 85M。

## 五、什么情况下值得回到微调

不是永久否定。以下任一条件成立时，微调（或蒸馏）重新变得合理：

1. **数据不能出本机**——如果是内部系统日志、简历原文这类敏感文本，云端 API 直接出局
2. **需要离线 / 私有化部署**——交付环境没有外网
3. **prompt 已到天花板**——比如 8B 在 recall 上稳定卡在 0.85 上不去，而 32B 能到 0.95，
   这时把 32B 的抽取结果当标答，蒸馏到 8B 才有意义（**先有高质量标答，再谈微调**）
4. **调用量级大到 API 成本超过训练成本**——百万条以上才可能出现
5. **要做的是分类而不是抽取**——这条现在就该做，只是底座换成 100M 级模型，不是 8B

顺序很重要：**先用云端大模型把标答做干净，再看需不需要蒸馏。** 反过来（先用词典标答训模型）
就是这次踩的坑。
