## 一、三条路线的技术差异

同一个任务（从 JD 抽技能 → 分类 → 统计频次），走过三条技术路线。差别不在"哪个更先进"，
而在**信息从哪来、一致性由谁保证、单位成本多高**。

| 维度 | 路线一：词典脚本 | 路线二：本地微调 8B | 路线三：云端 LLM + 本地确定性（当前） |
|---|---|---|---|
| 技能识别机制 | 正则 / 词表字面匹配 | LLM 生成，监督信号来自词典 | LLM 生成，边界规则由 prompt + 示例定义 |
| 标签来源 | 人工维护词表（400 词） | 词典自动标注（v1 并集平台标签） | 无训练；few-shot 示例 |
| 技能边界判断 | 取决于词表是否收录 | 继承词典口径，无法超越 | 显式定义（操作对象 / 领域名 / 指标词不抽） |
| 未登录技能覆盖 | 0（词典外一律漏） | 理论可泛化，实际无监督信号 | 强（LLM 先验知识） |
| 同义词归并 | 无，字面分裂 | 未处理 | 独立映射表，确定性归并 |
| 一致性 / 可复现 | 高（规则确定） | 中（生成式 + 版本漂移） | 抽取中（temp=0 + 后处理），分类高（映射表） |
| 14 万条 JD 耗时 | 分钟级 | 数天（12GB 单卡串行） | 10–18 小时（3–5 并发） |
| 单条边际成本 | 0 | 显存占用（电费级） | ≈¥0.0002 |
| 一轮迭代周期 | 改词表 → 重跑脚本 | 重标注 → 重训 2h → 重评估 | 改 prompt → 数十秒 |
| 硬件依赖 | 无 | 需 12GB GPU 常驻 | 无（CPU + 网络） |
| 可解释性 | 完全可追溯 | 黑盒 | 抽取命中可回溯到原文；映射表可逐条审计 |
| 交付/部署形态 | 本地脚本 | 需 GPU 环境 + 权重文件 | API Key + 脚本，无环境依赖 |

### 三条路线各自的瓶颈（技术机理）

**路线一：字面匹配没有语义层**
- 词表是枚举，无法判断"熟悉 Java 开发"里该抽 `Java` 而不抽整句，也无法判断
  "车辆 / 行人 / 道路"是被分割的操作对象，不是技能
- 未收录的词覆盖率为 0，而 JD 的长尾表达是开放集
- 没有归一化，同一技能的不同写法各自成键：清洗后得到 **34,594 个技能名**，
  而按 209 条规范名归一后仅 **208 种**——词表口径把频次统计打散成碎片分布
- 结论：适合"已知技能的频次巡检"，不适合"开放语料里的技能发现"

**路线二：监督信号与目标同源，上界被标答锁死**
- 设标注函数 `f(词典) = 标答`，训练得到 `g ≈ f`。由于 `f` 本身不含语义信息，
  `g` 的信息上界就是 `f` 的信息上界：**模型不可能超过生成标签的那本词典**
- 词典漏抽的技能没有正样本，模型没有任何梯度去学它；长尾恰好是模型唯一有存在价值的地方
- 因此信息增益为零：`g` 的输出 ≈ `f` 的输出，而 `f` 只需几十行正则即可运行（详见
  [`ModelFineTuning/README.md`](ModelFineTuning/README.md) 第二节）
- 附带的工程约束：1 epoch / 8982 条 = 2h01m（12GB 卡，batch=1），一轮迭代成本压不下来；
  14 万条本地推理按单卡串行吞吐需要数天

**路线三：把语义判断与一致性拆给两个组件**
- 抽取环节需要"读懂 JD 的边界"，这是 LLM 的先验知识带来的**新增信息**，词典和
  词典蒸馏模型都给不了
- 一致性环节（别名归并、硬/软二分类）**不能交给生成式模型**：同一技能在不同批次被判成
  不同类别，频次序列就不可比。所以放在映射表 + 100M 级分类器上，确定性、可审计、可 diff
- 长尾漏抽靠后处理黑名单兜底（领域词、指标词），而不是指望 prompt 100% 干净

## 二、为什么最后敲定路线三

三条硬约束同时成立时，解是唯一的：

| 约束 | 具体要求 | 排除的路线 |
|---|---|---|
| **信息源约束** | 抽取要覆盖开放集技能、要能区分对象词/领域词/指标词，即需要词典之外的新信息 | 排除路线一（无新信息）；排除路线二（信息上界 = 词典） |
| **一致性约束** | 频次统计要求"同一技能永远同一类"，跨批次可比、可复现、出错能定位 | 排除把二分类交给 8B 生成式模型的方案 |
| **成本约束** | 14 万条 × 多轮 prompt 迭代，单轮必须便宜且快 | 排除本地单卡推理（数天/轮）、排除为调边界而重训（2h/轮） |

交集只有一种组合：

```
语义判断（开放集、需先验知识） → 云端 LLM，prompt 驱动
一致性（归并、分类、可复现）   → 本地确定性代码（映射表 + 100M 分类器）
可批量、可断点、可审计          → 脚本编排，不用模型做调度
```

也就是说，路线三不是"路线二训不好所以换掉"，而是**把任务拆成两类性质不同的子问题**：
"读懂文本"交给生成式模型，"保持口径"交给确定性代码。前者的信息量来自预训练语料，
后者的可靠性来自没有随机性。

### 路线三的残余风险与兜底

| 风险 | 兜底 |
|---|---|
| 数据出域（招聘 JD 属公开信息，无合规障碍；若换内部数据需重评） | 敏感场景退回本地部署或脱敏后调用 |
| 供应商模型版本变更导致结果漂移 | 锁定模型 ID；抽样 200 条做版本回归，差异超阈值才升级 |
| prompt 边界靠人工试错 | 固定 dev 集（`../Cleaning/eval/jd-sample-10.txt` 前 5 条）+ test 集（后 5 条），迭代只看 dev，验收只看 test |
| 抽取仍有噪声 | 后处理黑名单增量维护，误抽一条加一行，可累积 |

## 三、归档条目

### 1. `ModelFineTuning/` — Qwen3-8B 岗位技能抽取微调（2026-10）

Unsloth + QLoRA 微调 `Qwen3-8B` 做「JD → 技能抽取」，训练 8982 条 / 测试 498 条 / 208 技能。

**技术原因**：监督信号来自 209 条正则词典，标注函数与新任务同源，模型输出上界被标答
锁死（信息增益为零）；长尾技能无正样本、无梯度；12GB 单卡 `batch=1` 下 1 epoch 需 2h01m，
一轮边界调整的重训成本与之绑定，无法支撑 prompt 级的高频试错。

→ 详见 [`ModelFineTuning/README.md`](ModelFineTuning/README.md)

### 2. `DataPreprocessing/` — 词典 + 脚本做清洗与三表建模（2026-10）

`DataCleaning.py`（读 CSV → 文本清洗 → 400 词词典抽技能 → 按 `(岗位, 技能, 公司)` 去重 →
导出 Excel/SQL）+ `ExportSQL.py`（拆成 `skill` / `position` / `skill_position` 三表）。
产出 34,594 技能 / 56,755 岗位 / 508,536 关联，孤儿关联 0。

**技术原因**：正则/词表只有字面匹配、没有语义层，无法区分"技能"与"被操作对象""领域名"
"考核指标"；开放集未登录词覆盖率为 0；缺归一化导致同一技能按写法分裂（34,594 个键
对应实际 208 种规范技能），频次分布失去可比性。三表模型只能表达"岗位—技能"共现，
无法表达方向/层级，也不支持把技能按类别聚合。

→ 详见 [`DataPreprocessing/README.md`](DataPreprocessing/README.md)

### 3. `vue+springboot/` — 上一版 pcscp 平台

Spring Boot + Neo4j + Vue3 + ECharts 的课程 / 技能 / 岗位知识图谱系统。

**技术原因**：运行时依赖三套外部服务（MySQL + Neo4j + Redis）加前后端两套构建，部署链路长、
打包上线成本高；数据规模在千级节点，力导向图由 ECharts 前端直接渲染即可，图数据库的
查询能力没有对应的使用场景。改为 MediaWiki 承载内容（单进程 + PHP + SQLite，页面即数据，
`ingest.py` 可重复重建），图谱仍由前端渲染。

→ 项目移入本目录归档；现役实现见 [`../test/wiki/`](../test/wiki/)
