### v3 实测结论（30 条，2026-11-03）

- v2 → v3 **零变化**：`3yxz-000` 输出与 v2 完全一致（temperature=0 下的确定性输出，也证明脚本参数链路正确）
- 示例 2 教会了「操作对象不抽」（车辆/行人 等 4 词始终未出现），但**领域名与考核指标压不住**——与 CHANGELOG 早前的预期一致（目标 C「预期无法达成」）
- 结论：prompt 侧到此为止，剩余噪声按既定方案交给 blocklist 后处理；本次 v4 的改动属于「最后一轮 prompt 微调 + 接线」，**不再继续往 prompt 里加禁止条目**

## v3 待验证的点

用 `eval/jd-sample-10.txt` 第 1 条（`3yxz-000`）重测，**新开会话**、`temperature=0`、`top_p=1`：

- 目标 A：`车辆`、`行人`、`道路`、`障碍物` 消失（v2 未达成，靠示例 2 压）
- 目标 B：`LabelMe`、`CloudCompare`、`点云语义分割`、`实例分割` 保留（recall 不能掉）
- 目标 C（预期无法达成）：`自动驾驶`、`机器人导航`、`标注准确率`、`质量标准` 消失

若 A、B 达成而 C 未达成，即确认 prompt 已到 8B 上限，剩余噪声交 `../rules/blocklist.yaml`
处理，不再继续加规则。

## 改 prompt 的四条规矩

1. **一次只改一处**。同时动规则和示例，指标变化无法归因
2. **只在 dev 集上调**（`jd-sample-10.txt` 第 1–5 条）。第 6–10 条是 test 集，定稿前不许看结果
3. **示例不得取材于 test 集**。v3 的示例 1、2、3 分别对应第 4、1、5 条，都在 dev 集内，
   所以这三条的高分不能作为效果证据
4. **每轮结果落盘**到 `eval/results/`，文件名带日期与轮次，便于回看指标趋势

## 已知边界（写进报告时要说清）

- 抽取任务**优先保 recall**：漏抽的技能无法恢复，多抽的可以靠黑名单过滤
- 8B 在「对象词 / 领域词 / 指标词」三类上的判别不稳定，本质是指令跟随容量限制，
  换更大的模型能改善但成本上升；当前选择是「prompt 尽力 + 规则兜底」
- prompt 对**长 JD 尾部**覆盖较弱，超过 3000 字符截断，实测 BOSS JD 多在 1500 内，可接受
